# 토크나이저 선정

상태: 확정.

- **청크 길이 단위**: 선정 임베딩(Qwen3-Embedding-0.6B)의 자체 토크나이저 토큰 수
- **BM25 토큰화**: `word`(소문자화, 영문/숫자/밑줄 묶음과 한글 묶음 단위 분리, 어간 추출 없음). 형태소 분석기 kiwi, okt, kkma도 비교했고 일관된 이득이 없어 기각

## 질문

토크나이저의 용도는 두 가지이고, 각각 따로 고른다.

1. 청크 크기를 무엇으로 셀 것인가. Chunking 실험의 크기 후보(256, 512, 1024)가 실제 임베딩 입력 크기와 맞아야 크기 변인이 통제된다.
2. BM25 sparse 검색에서 문서와 질의를 어떤 단위로 나눌 것인가. Part C Hybrid 검색의 sparse 쪽 품질을 정한다.

## 고정한 변인

| 변인 | 값 |
|---|---|
| Corpus, 정제 | `uv_docs` 81개 문서, Ingest 최소 구현 |
| DB | Qdrant(gRPC). sparse 벡터와 IDF modifier, 항상 전수 계산 |
| 임베딩 | Qwen3-Embedding-0.6B(선정), multilingual-e5-large(2위, 교차 확인 대상) |
| 질의 | dev set 답 있는 30문항. 영어 정본과 한국어 번역 묶음 |

## 청크 길이 단위

### 후보와 방법

| 후보 | 설명 |
|---|---|
| `chars` | 문자 수. 의존성이 없다 |
| `tiktoken_o200k` | OpenAI 계열 BPE. LLM 입력 토큰 수의 근사치 |
| `qwen3` | 선정 임베딩의 자체 토크나이저(특수 토큰 포함). 기준 단위 |
| `e5` | 2위 임베딩의 토크나이저. 교차 확인 단계에서 잘림이 생기는지 보려고 함께 쟀다 |

1. Corpus를 고정 문자 길이 500, 1000, 2000, 4000자로 나눈다.
2. 청크마다 네 단위로 길이를 재고, 기준 단위(qwen3 토큰 수)에 대한 비율의 분포를 구한다.
3. 목표 토큰 수(256, 512, 1024)를 문자 수 상한으로 맞추는 두 가지 규칙을 실제로 적용해 본다. 평균 비율 규칙은 목표에 평균 문자/토큰 비율을 곱하고, 최소 비율 규칙은 관찰된 최소 비율을 곱한다. 각 규칙으로 Corpus를 다시 자르고 실제 qwen3 토큰 수를 잰다.

측정 도중 문제를 하나 발견했다. fastembed의 `token_count`는 모델 최대 입력에서 잘린 뒤의 수를 돌려준다(e5는 512에서 멈춘다). 그래서 잘림을 끈 토크나이저 사본으로 세도록 `EmbeddingClient.token_count`를 고쳤다. Embedding 선정 실험의 최대 청크는 480토큰으로 모든 후보의 상한 아래였으므로 그 결과는 바뀌지 않는다.

### 해석

- **문자 수로는 크기를 통제할 수 없다.** 코드 블록, 경로, 플래그가 많은 청크는 문자당 토큰이 두 배 이상 많다(문자/토큰 최소 1.45, 평균 4.09). 평균 비율 규칙은 청크의 27~39%가 목표를 넘는다. 넘지 않게 최소 비율 규칙을 쓰면 청크가 목표의 1/3 크기로 줄어든다. 어느 쪽이든 Chunking 실험에서 "512토큰"이라고 부른 조건이 실제 512토큰이 아니게 된다.
- **tiktoken은 평균으로는 qwen3와 거의 같다(0.98, 변동계수 0.03).** 하지만 최소 비율이 0.76이라, tiktoken 512토큰인 청크가 qwen3로는 최대 약 670토큰까지 간다. 정확히 맞추려면 약 25% 여유가 필요하다.
- **qwen3 토크나이저는 정의상 정확하다.** 별도 의존성도 없다(fastembed가 이미 쓰는 `tokenizers`).
- **e5는 qwen3보다 평균 22% 더 많이 센다(최대 2배).** qwen3 512토큰 청크는 e5 입력 512를 넘을 수 있다. 교차 확인(7단계)에서 Chunking 크기가 512 이상으로 정해지면 e5는 잘린 채로 비교된다. 그때 e5의 잘림 비율을 함께 기록한다.

### 판정

계획서의 기준은 "잘림 0%를 보장하면서 가장 단순한 것"이었다. 그대로 적용하면 `chars`가 된다. 선정 임베딩의 최대 입력이 32,768토큰이라 어떤 단위로 1024 크기를 잡아도 잘리지 않기 때문이다.

**이 기준을 따르지 않았다.** 이 기준은 임베딩 최대 입력이 512 근처일 때를 가정하고 세운 것이다. 최대 입력이 커지면서 실제 위험은 잘림이 아니라 크기 변인이 통제되지 않는 것으로 바뀌었다. 문자 단위로는 위 표처럼 Chunking 실험의 크기 조건이 27~39% 어긋나거나 1/3로 줄어든다.

**결정: 청크 길이는 qwen3 토크나이저 토큰 수로 잰다.** Chunking 실험의 분할기는 `EmbeddingClient.token_count`(잘림 없는 수)를 길이 함수로 받는다. 7단계에서 임베딩이 e5로 바뀌면 길이 단위도 e5 토크나이저로 바뀐다. 인덱스 계약의 `chunk_config_hash`에 길이 단위를 포함한다.

tiktoken은 파이프라인에 넣지 않는다. LLM 입력 토큰은 엘리스 API 응답의 `usage`가 정확한 값이다. 사전 추정이 필요하면 qwen3 토큰 수가 tiktoken과 평균 2% 안이라 그것을 쓴다.

## BM25 토큰화

### 후보

단순한 순서로 나열한다. 형태소 분석기 세 개는 외부 라이브러리라 규칙 기반 후보보다 뒤에 둔다. 그중 kiwi는 pip만 있으면 되고, okt와 kkma는 JVM(KoNLPy)이 필요하다.

| 후보 | 규칙 | 필요한 것 |
|---|---|---|
| `whitespace` | 소문자화, 공백 분리, 토큰 양끝 구두점 제거 | 없음 |
| `word` | 소문자화, `[a-z0-9_]+` 묶음과 `[가-힣]+` 묶음으로 분리. `uv.lock이`가 `uv`, `lock`, `이`가 된다 | 없음 |
| `word+stem` | `word`에 Snowball 영어 어간 추출 추가 | snowballstemmer |
| `word+stem+ident` | `word+stem`에 코드 식별자(`uv.lock`, `--frozen`, `pyproject.toml`)를 통째로 하나 더 남김 | snowballstemmer |
| `kiwi` | Kiwi 형태소 분석 결과(form). 글자나 숫자가 없는 토큰은 버림 | kiwipiepy |
| `okt` | Okt(KoNLPy) 형태소 분석 결과. 같은 규칙으로 정리 | konlpy, JVM |
| `kkma` | Kkma(KoNLPy) 형태소 분석 결과. 같은 규칙으로 정리 | konlpy, JVM |

형태소 분석기는 질의뿐 아니라 영어 문서에도 똑같이 적용했다. Ingest와 Query가 같은 토크나이저를 써야 같은 단어가 같은 index로 가기 때문이다. 그래서 이 비교는 한국어 처리와 함께 영어 기술 문서 처리도 평가한다.

형태소 분석기는 실험 전용 이미지(`batch-korean`, JRE 포함)에서만 설치한다. 의존성 그룹은 `korean`이다. 운영 이미지에는 들어가지 않는다.

### 방법

BM25 가중치는 문서 쪽에 넣었다. 단어 빈도 포화 k1=1.2, 길이 정규화 b=0.75이고 Corpus에 맞춰 조정하지 않았다. IDF는 Qdrant의 IDF modifier가 곱한다. 질의는 등장한 단어마다 값 1이다. 토큰은 crc32로 2^20 공간에 해시하므로 질의 쪽에 어휘 사전이 필요 없다. 청크는 고정 1,000자(587개)로 Embedding 실험과 같다. sparse 단독 top-10으로 근거 단위 지표를 쟀다.

판정 기준은 계획서의 "주 지표(Hit@5, MRR) 우선, 신뢰구간 안이면 단순하고 설치 쉬운 쪽"이다. 영어와 한국어 질의 모두에 적용한다.

### 해석

- **한글 토큰은 어느 분석기를 써도 문서와 한 번도 맞지 않는다.** 문서가 영어라서다(0/390~0/816). 형태소 분석기가 한국어를 더 잘 나눠도 BM25 점수에는 기여하지 않는다. 한국어 질의에서 BM25가 기댈 수 있는 것은 번역되지 않은 영어 식별자뿐이다.
- **점수 차이는 영어 문서를 어떻게 나누느냐에서 생긴다.** 질의 쪽 영어 토큰은 kiwi와 `word`가 거의 같았다. 반면 문서 쪽에서 kiwi는 영어 기술 용어를 사전에 없는 말로 보고 쪼갠다.
  - `pyproject.toml`이 `pypr` + `oject.toml`(329회)이 된다.
  - `requirements.txt`가 `...ments.txt`(105회)가 된다.
  - `dependencies`가 `depende` + `ncies`가 된다.
  - 반대로 `uv.lock`, `3.12`, `tool.uv.index` 같은 식별자와 버전은 통째로 남는다.
  
  영어 MRR +0.04는 이 두 효과가 섞인 결과이고, 한국어 질의에서는 반대로 -0.05가 나왔다. 일관된 이득이 아니다.
- **okt는 `word`와 사실상 같다.** 네 지표 모두 차이가 0이거나 구간이 0을 포함한다. 그런데 JVM이 필요하고 약 100배 느리다.
- **kkma는 한국어 MRR이 유의하게 낮고(-0.07) 가장 느리다(3.5초/청크 1천 개).**
- **whitespace는 한국어에서 유의하게 떨어진다.** `uv.lock이`, `--frozen을`처럼 조사가 붙은 식별자가 문서 토큰과 맞지 않기 때문이다.
- **BM25 단독이 dense보다 낮지 않다.** 영어 BM25(`word`) Hit@5 0.933은 Qwen3 dense 0.833과 bge-base dense 0.933 이상이다. 한국어에서는 0.567로 Qwen3 dense 0.767보다 낮다. 두 방식이 잘 찾는 문항이 다를 수 있어 Part C Hybrid 가설을 뒷받침한다.

### 판정

1. 두 언어의 주 지표 네 개 중 하나라도 `word`보다 유의하게 낮은 후보를 뺀다. whitespace(한국어 둘)와 kkma(한국어 MRR)가 빠진다.
2. kiwi는 영어 MRR이 유의하게 높다. 하지만 구간 하한이 0.002로 경계이고, 한국어에서는 반대 방향(-0.05, 구간 상한 0.006)이다. 원인도 영어 단어를 잘못 쪼개는 동작이 섞인 것이라 일관된 이득으로 보지 않는다.
3. 남은 `word`, `word+stem`, `word+stem+ident`, `okt`, kiwi는 주 지표가 같다고 보고 단순성으로 가른다. 의존성이 없고 가장 빠른 `word`를 고른다.

**결정: `word`.** `TextTokenizer("word")`이고 인덱스 계약의 토크나이저 이름은 `word`다.

kiwi에서 관찰한 "식별자와 버전 번호를 통째로 남기는 효과"는 Part C 개선 후보로 남긴다. 단, 어간 추출 없이 `word`에 식별자만 더하는 방식으로 시험한다. 이번 `word+stem+ident`는 어간 추출과 식별자 보존을 함께 넣어 두 효과를 분리하지 못했다.

## 한계

- dev set 30문항이라 95% 구간 반폭이 약 0.13이다. 어간 추출이나 kiwi의 작은 효과(약 0.03~0.07)는 확정할 수 없다.
- 형태소 분석기는 기본 사전과 설정으로 썼다. 사용자 사전에 기술 용어를 넣으면 kiwi의 영어 쪼개기는 줄어들 수 있다.
- BM25 k1, b는 통상값이다. 조정은 Part C 후보로 남긴다.
- 문자/토큰 비율은 이 Corpus(코드가 많은 기술 문서)에서 잰 값이다. 산문 위주 Corpus에서는 문자 단위의 오차가 더 작을 수 있다.
- 최소 비율 규칙의 최소값은 관찰값이다. 새 문서가 들어오면 더 낮은 비율이 나올 수 있다. 이 점도 문자 단위를 기각한 이유다.

## 재현

```
make tok-bench   # batch-korean 이미지(JRE, korean 의존성 그룹)로 실행. Qdrant 기동, 길이 단위 측정(Qwen3, e5 토크나이저 로드), BM25 후보 7종 색인과 측정, Qdrant 정지. 모델 파일은 Embedding 실험에서 받은 캐시를 재사용
```

결과는 `research/artifacts/tokenizer/`에 저장된다.

- `length_units.json`: 단위별 비율, 문자 상한 검사
- `sparse_results.json`: 요약과 신뢰구간
- `sparse_per_question.jsonl`: 문항별 판정
- `sparse_comparison.json`: 1위 대비 짝지은 차이
