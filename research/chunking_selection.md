# Chunking 전략 선정

상태: 확정(**`structure-512-77`**, 문서 구조 분할, 최대 512 Qwen3 토큰, 겹침 77토큰). 사전 판정 규칙은 1단계에서 재귀 분할, 2단계에서 `structure-256-0`을 골랐고, 프로젝트 작성자가 두 번 모두 규칙의 결과를 바꿨다. 경위는 "계획과 달라진 점"에 있다.

## 질문

어떤 분할 방식과 크기가 근거를 끊지 않으면서 검색 정확도가 가장 높은가.

## 후보

모든 방식이 길이를 Qwen3 토크나이저 토큰 수로 재고(토크나이저 선정 결정), 크기 상한을 넘지 않게 자른다. 방식은 자르는 경계만 다르다(`app/service/ingest/chunk_splitter.py`의 `ChunkSplitter`).

| 방식 | 자르는 곳 | 1단계 겹침 |
|---|---|---|
| `fixed` | 단어 경계. 상한까지 단어를 채운다 | 15% |
| `sliding` | `fixed`와 같은 창을 절반씩 민다 | 50% |
| `recursive` | 문단, 줄, 문장, 단어 순으로 큰 경계부터. 상한을 넘는 조각만 다음 경계로 쪼개고, 조각은 상한까지 이어 붙인다 | 15% |
| `structure` | Markdown 제목마다 절을 나눈다(코드 블록 안 `#` 줄 제외). 상한 안의 절은 쪼개지 않고 이웃 절과 묶고, 상한을 넘는 절만 재귀 분할한다 | 15%(한 절을 나눌 때만) |
| `semantic` | 문단과 문장 끝에서 나눈 문장을 Qwen3로 임베딩하고, 이웃 문장 거리가 문서 안 95 백분위를 넘는 곳에서 자른다. 상한을 넘는 묶음만 문장 단위로 채운다 | 15%(상한을 넘는 묶음을 나눌 때만) |

`sliding`과 `semantic`은 계획 수립 뒤에 후보로 추가했다.

## 고정한 변인

| 변인 | 값 |
|---|---|
| Corpus, 정제 | `uv_docs` 81개 문서 |
| 임베딩 | Qwen3-Embedding-0.6B(잠정 선정). 크기 상한 32,768이라 256, 512, 1024 모두 가능 |
| 저장과 검색 | Qdrant 정확 검색 모드, dense top-10 |
| 질의 | dev set 답 있는 30문항. 영어 정본과 한국어 번역 묶음 |

## 방법

전체 조합(방식 5 × 크기 3 × 겹침 2)을 돌리지 않고 두 단계로 나눴다.

1. 다섯 방식을 크기 512로 비교한다.
2. 1단계에서 고른 방식만 크기 256, 512, 1024와 겹침 0%, 15%로 다시 잰다(`sliding`이 이겼다면 겹침 25%, 50%).

지표:

- 주 지표: 근거 단위 Hit@5, MRR@10(Embedding 선정과 같은 판정)
- 근거 보존율: 근거 구절이 같은 문서의 한 청크 안에 통째로 들어간 문항 비율(문항의 모든 구절이 보존돼야 함). Hit@k는 구절의 일부만 걸려도 성공으로 치지만, 잘린 근거는 생성 단계에서 불완전한 답이나 Hallucination으로 이어진다.
- 질의당 근거 토큰 수: 상위 5개 청크의 Qwen3 토큰 합. LLM 입력 비용의 근사치다.
- 청크 수, 평균과 최대 토큰, 분할 시간, 색인 시간

판정 규칙(실험 전에 정하고 `pick_best`로 구현):

1. 두 언어 Hit@5 평균이 가장 높은 설정을 1위로 둔다(같으면 MRR).
2. 영어, 한국어 모두에서 1위와 Hit@5 짝지은 차이의 구간이 0을 포함하는 설정만 남긴다.
3. 그중 근거 보존율이 높은 쪽, 같으면 근거 토큰 수가 적은 쪽, 그래도 같으면 단순한 쪽(`fixed`, `sliding`, `recursive`, `structure`, `semantic` 순).

### 구현 중 바로잡은 것

처음에는 조각마다 토큰 수를 세어 더했다. 단어 단위로 자르면 경계마다 토큰이 하나씩 더 세어져(`"word "`가 2토큰), 크기 512로 설정한 `fixed` 청크가 실제로는 평균 323토큰이었다. 크기 조건이 방식마다 달라지는 문제라, 문서를 한 번 토큰화하고 토큰 위치로 구간 길이를 세도록 고쳤다. 청크를 확정하기 전에는 실제 토큰 수를 한 번 더 세어 상한을 넘으면 뒤 조각을 뺀다. 모든 설정에서 상한을 넘은 청크는 0개다.

### 해석

- **`fixed`와 `semantic`은 한국어 질의에서 유의하게 낮다.** `fixed`는 문단 중간에서 잘라 근거 구절 2개를 갈랐다(보존율 0.933). `semantic`은 청크가 평균 264토큰으로 작아져, 근거 토큰은 가장 적지만 검색이 떨어졌다. 문장 5,671개를 임베딩하느라 분할에만 12분 넘게 걸려 Ingest 비용도 가장 크다.
- **`sliding`은 근거를 모두 보존하지만 청크가 46% 많고 색인이 40% 느리다.** 겹침 50%라 같은 내용이 두 번 들어간다. 상위 5개 안에 겹치는 청크가 함께 올라오면 LLM 입력에 같은 문장이 중복된다.
- **`structure`는 Hit@5와 MRR이 가장 높고 근거 토큰이 가장 적다(`recursive`보다 16% 적음).** 하지만 multi_doc 문항 하나의 384자 근거 구절(`reference/troubleshooting/build-failures.md`)이 상한을 넘는 절 안에서 두 청크로 갈려 보존율이 0.967이다.
- **`structure`와 `recursive`의 차이는 판정 경계에 있다.** Hit@5 차이는 영어 +0.03 [0.00, 0.10], 한국어 +0.07 [0.00, 0.17]로 구간 하한이 0.0이고, MRR 차이는 영어 +0.03 [-0.05, 0.12], 한국어 +0.04 [-0.08, 0.18]이다.

판정 규칙의 결과: 1위 `structure`와 차이가 없는 후보는 `sliding`, `recursive`, `structure`다. 근거 보존율 1.000인 `sliding`, `recursive`가 남고, 근거 토큰이 적은 `recursive`가 뽑힌다. 실제 채택은 **`structure`**다("계획과 달라진 점" 참고).

근거 토큰 수는 영어 질의 기준이다. 1위는 `structure-512-77`이다(512-0과 Hit@5가 같고 MRR 평균이 앞섬). 1위 대비 Hit@5 짝지은 차이는 모든 설정에서 구간이 0을 포함한다(1024는 영어, 한국어 모두 +0.10 [0.00, 0.23]). 근거 보존율도 모두 0.967(같은 multi_doc 구절 하나)이라, 판정 규칙은 근거 토큰이 가장 적은 `structure-256-0`을 고른다.

- 256은 근거 토큰이 절반 이하지만, 한 구절이 여러 청크로 흩어져 근거 보존@5가 영어 0.20, 한국어 0.17 낮다. 한국어 Hit@5도 0.07 낮다(구간은 0을 포함).
- 512에서 겹침은 거의 영향이 없다. 겹침은 상한을 넘는 절을 나눌 때만 들어가서 청크가 4개만 늘었다. 근거 보존@k는 같고, MRR은 영어에서 겹침 0이, 한국어에서 겹침 77이 앞선다.
- 1024는 Hit@5가 두 언어 모두 0.10 낮고 근거 토큰은 약 2배다. 짧은 절이 상한까지 이웃 절과 묶여 청크 하나에 주제가 여럿 섞이는 쪽이다(추정).

## 결정

**`structure-512-77`**: 문서 구조 분할(Markdown 제목 단위, 상한을 넘는 절만 재귀 분할), 최대 512 Qwen3 토큰, 겹침 77토큰. 인덱스 계약의 Chunk 설정 이름은 `structure-512-77`이다.

기각한 후보:

- `fixed`, `semantic`: 한국어 Hit@5가 1위보다 유의하게 낮다. `semantic`은 분할 비용도 가장 크다.
- `sliding`: 1위와 차이는 없지만 근거 토큰과 청크 수, 색인 시간이 가장 크다.
- `recursive`: 근거 보존율 1.000으로 사전 규칙의 1단계 선택이었다. 주 지표(Hit@5, MRR)에서 모두 뒤지고, 근거 보존@5도 영어 0.767, 한국어 0.633으로 `structure-512-77`(0.867, 0.800)보다 낮다.
- `structure-256-0`, `structure-256-38`: 사전 규칙의 2단계 선택. 근거 보존@5가 0.60~0.67로 낮다.
- `structure-512-0`: 근거 보존@k는 같고 근거 토큰은 16토큰 적다. 한국어 MRR이 0.025 낮아 한국어 질의를 우선해 겹침 77을 남겼다(차이는 구간 안).
- `structure-1024-*`: Hit@5가 0.10 낮고 근거 토큰이 약 2배다.

## 계획과 달라진 점: 판정 규칙을 넘어 문서 구조 분할, 512, 겹침 77 채택

### 1단계: 재귀 분할 대신 문서 구조 분할

1단계 사전 규칙(Hit@5, 근거 보존율, 근거 토큰 수 순)은 재귀 분할을 골랐다. 프로젝트 작성자가 이 결과를 검토하고 문서 구조 분할로 바꿨다. 판단 근거는 다음과 같다.

> 30문항 중 1문항 차이로 재귀 분할이 채택된 것이라면, 영어와 한국어 Hit@5가 더 높은 방식으로 가고, 근거 보존은 생성 단계에 넣는 청크 수(k)를 높여 보완하는 절충안이 낫다.

이 판단을 받친 수치:

- 재귀 분할이 이긴 단계는 근거 보존율 하나이고, 차이는 30문항 중 1문항(1.000 대 0.967)이다. 갈린 구절은 multi_doc 문항의 384자 구절 하나다.
- 문서 구조 분할은 주 지표에서 모두 앞선다. Hit@5 영어 +0.03, 한국어 +0.07(구간 하한 0.0), MRR 영어 +0.03, 한국어 +0.04(구간이 0을 포함). 판정 규칙상 차이 없음이지만 방향은 일관되다.
- 질의당 근거 토큰이 16% 적다(1,843 대 2,185). 같은 토큰 예산에서 k를 늘릴 여유가 있다.

보완책을 확인하려고 **근거 보존@k**를 새로 잰다. 상위 k개 청크가 문항의 근거 구절 전체를 덮는 비율이다(구절의 모든 글자가 같은 문서의 상위 k 청크 어딘가와 20자 이상 이어서 일치해야 함). 근거 보존율은 "한 청크 안에 통째로" 들어갔는지를 보지만, 생성 단계에는 상위 k개가 함께 들어가므로 갈린 구절도 조각이 모두 검색되면 온전히 쓸 수 있다.

결과적으로 절충안이 성립했다. 같은 크기 512에서 근거 보존@5는 문서 구조 분할이 영어 0.867, 한국어 0.800이고 재귀 분할이 0.767, 0.633이다. 근거 보존@10도 0.867, 0.833 대 0.833, 0.700이다. 한 청크 안의 보존율은 1문항 지지만, 생성 단계에 실제로 들어가는 상위 k개 기준으로는 앞선다.

### 2단계: 256 대신 512

2단계 사전 규칙은 모든 설정이 Hit@5와 보존율에서 같아 근거 토큰이 가장 적은 `structure-256-0`을 골랐다. 이 선택은 1단계에서 문서 구조 분할을 택한 근거(Hit@5와 근거 보존@k를 높인다)와 어긋난다. 256은 근거 보존@5가 영어 0.667, 한국어 0.633으로 512(0.867, 0.800)보다 낮고, 한국어 Hit@5도 0.867로 512(0.933)보다 낮다. 그래서 프로젝트 작성자가 1단계와 같은 기준으로 512를 택했고, 겹침은 1단계 비교 설정 그대로 77을 둔다.

사전 규칙이 두 번 모두 작성자 판단과 갈린 이유: 규칙은 "한 청크 안의 보존율"과 "근거 토큰 수"를 Hit@5 다음 기준으로 뒀는데, 이 둘은 생성 단계에 넣는 문맥의 질을 직접 재지 않는다. 다음 선정 실험(7단계 이후)에서 Chunking 결과를 비교할 일이 있으면 근거 보존@k를 근거 토큰 수보다 앞에 둔다.

`verdict.json`은 규칙의 출력을 그대로 남긴다. `method`에 규칙의 선택(`rule_choice: recursive`)과 실제로 쓴 방식(`used: structure`)이 있고, `by_size_and_overlap.chosen`은 규칙의 선택(`structure-256-0`)이다. 최종 설정은 이 문서의 "결정"이 정본이다. 재현할 때는 `make chunk-bench`(`CHUNK_METHOD` 기본값 `structure`)로 2단계를 문서 구조 분할로 돌린다.

## 다음 단계에 주는 영향

- **7단계(Embedding 교차 확인)**: Embedding 선정 기록은 "Chunking이 512토큰 이하로 정해지면 비용 규칙에 따라 e5로 바꾼다"고 정했다. 크기가 512 Qwen3 토큰으로 정해졌으므로 이 조건이 걸린다. 다만 e5는 Qwen3보다 평균 22% 많이 세서(토크나이저 선정), Qwen3 512토큰 청크 일부가 e5 입력 512를 넘어 잘린다. 문서 구조 분할은 평균 347토큰이라 재귀 분할(423)보다 잘림이 적을 것으로 본다(추정). 7단계에서 e5의 잘림 비율을 함께 기록하고, e5로 바꾸면 길이 단위도 e5 토크나이저로 바꿔 Chunking을 다시 실행한다.
- **8단계**: 생성 단계의 k는 근거 보존@5(0.867, 0.800)와 @10(0.867, 0.833)을 보고 정한다. 한국어는 k를 10으로 늘리면 근거 보존이 0.033 오른다.
- **8, 9단계**: 질의당 근거 토큰은 상위 5개 기준 약 1,840토큰, 상위 10개면 약 3,700토큰이다(추정, 평균 청크 347토큰 기준). LLM 비용 추정에 이 값을 쓴다.

## 한계

- dev set 30문항이라 구간 반폭이 약 0.13이다. 여러 차이가 구간 하한 0.0의 경계에 걸려 있다(`structure` 대 `recursive`, `sliding`, 2단계 1024).
- 근거 보존율은 30문항 중 1~2문항 차이로 갈렸다. 판정 순서상 영향이 크지만 표본은 작다.
- 1단계 겹침은 `sliding`만 50%라 방식과 겹침이 함께 바뀐다. `sliding`의 정의상 피할 수 없다.
- `semantic`은 문장 하나씩 임베딩했다. 앞뒤 문장을 묶는 설정(LangChain `buffer_size=1`)과 백분위 값(95)은 바꿔 보지 않았다.
- 청크 앞에 제목 경로를 붙이는 방식은 비교하지 않았다. 청크 내용을 바꾸는 별도 변인이라 Part C 후보로 남긴다.
- 색인 시간은 Docker CPU 한 번 측정값이다.

## 재현

```
make chunk-bench   # Qdrant 기동, 1단계 5개와 2단계 5개 설정 색인과 측정, Qdrant 정지(CPU에서 약 1시간)
```

결과는 `research/artifacts/chunking/`에 저장된다.

- `results.json`: 설정과 언어별 요약, 신뢰구간, 근거 보존율, 근거 토큰 수, 시간
- `per_question.jsonl`: 문항별 판정
- `verdict.json`: 두 단계의 1위, 1위 대비 Hit@5 짝지은 차이, 선택
