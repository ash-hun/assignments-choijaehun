# Gold Set과 Metric 선정

상태: 설계 확정, 파일럿 전. 지표 목록, Gold Set 구성, 재현성 확보 방법, 실시간 누적 평가 방식과 이후 검증의 통과 기준을 정한다. uv 문서 루브릭은 v1(8항목)으로 확정했고, 파일럿과 Judge 검증 결과는 이 문서 뒤쪽에 이어서 기록한다.

## 질문

1. 이 서비스의 검색, 생성, 운영을 각각 어떤 지표로 재야 Part C에서 원인을 짚을 수 있는가.
2. 그중 정답 없이 잴 수 있는 지표는 무엇이고, 실제 사용자 질의마다 누적해 보여줄 수 있는가.
3. 최종 평가용 test set은 어떻게 구성하고 dev set과 어떻게 분리하는가.
4. seed를 고정할 수 없는 모델로 평가 결과를 어떻게 재현하는가.

## 선행 평가 체계 조사

RAG 평가 체계 네 가지의 지표 정의와 판정 방식을 보고, 이 프로젝트에 채택, 변형, 미채택한 항목을 정했다.

| 체계 | 지표 | 판정 방식 | 정답 필요 |
|---|---|---|---|
| RAGAS | Faithfulness, Response Relevancy, Context Precision, Context Recall | LLM이 답을 주장으로 나눠 근거로 뒷받침되는지 판정. Response Relevancy는 답에서 질문을 역생성해 원 질문과 임베딩 유사도를 잰다 | Faithfulness, Response Relevancy는 불필요. Context Recall은 정답 답변 필요 |
| ARES | Context Relevance, Answer Faithfulness, Answer Relevance | 합성 데이터로 파인튜닝한 경량 Judge. 사람 라벨 소량(150개 이상)으로 Judge 오차를 보정하고 신뢰구간을 내는 PPI(prediction-powered inference) | Judge 학습과 보정에 사람 라벨 필요 |
| RAGChecker | 전체 claim 단위 Precision, Recall, F1. 검색: claim recall, context precision. 생성: context utilization, noise sensitivity, hallucination, self-knowledge, faithfulness | 답과 정답을 claim으로 나누고 근거와의 함의(entailment)로 판정 | 정답 claim 필요 |
| TruLens RAG triad | Context Relevance, Groundedness, Answer Relevance | Judge 피드백 함수를 앱 호출마다 붙여 기록 | 불필요(운영 트래픽에 바로 쓸 수 있음) |

### 채택, 변형, 미채택

| 항목 | 결정 | 이유 |
|---|---|---|
| Context Precision, Context Recall(RAGAS) | **변형 채택** | Judge 판정 대신 기존 근거 구절 규칙(60자 창 일치)으로 Recall@k, Precision@k를 잰다. 규칙 판정은 비용이 0이고 다시 돌려도 값이 같다 |
| claim 단위 정답 대조(RAGChecker) | **변형 채택** | 정답 답변을 claim으로 나누는 대신 문항마다 사람이 쓴 `acceptance_criteria` 요점과 대조한다. uv 답변 정확성의 "핵심 요점" 항목이 이 판정을 맡는다. 요약 문항처럼 정답 문장이 하나로 정해지지 않는 경우에도 쓸 수 있다 |
| 인용 단위 근거 대조 | **채택** | 이 서비스는 문장마다 `[n]` 인용을 단다. 인용한 청크가 그 문장을 뒷받침하는지를 Citation Precision으로 잰다 |
| 실시간 기록과 지표 부착(TruLens) | **채택** | 질의마다 기록을 남기고 Judge를 뒤따라 붙이는 구조를 실시간 누적 평가에 쓴다 |
| Faithfulness, Groundedness(RAGAS, TruLens) | **미채택** | 인용이 달린 문장의 근거 대조는 Citation Precision이 맡는다. 인용 없이 지어낸 문장은 재지 못한다(한계 절) |
| Answer Relevance(TruLens, ARES) | **미채택** | Gold Set에서는 uv 답변 정확성이 "질문에 맞게 답했는가"를 정답과 대조해 더 엄격하게 잰다 |
| Response Relevancy의 역생성 방식(RAGAS) | **미채택** | 값이 임베딩 모델에 따라 달라지고, 거절 응답과 짧은 정답을 구분하기 어렵다 |
| Context Relevance(TruLens, ARES) | **미채택** | 청크마다 Judge를 부르면 질의당 호출이 5회 늘어난다. 실시간에서는 검색 최고 점수 분포가 검색 품질의 비용 0 대리 지표가 되고, Gold Set에서는 규칙 기반 Precision@k가 같은 것을 잰다 |
| noise sensitivity, context utilization(RAGChecker) | **미채택** | 정답 claim 집합과 claim별 함의 판정이 필요해 Judge 호출이 문항당 수십 회로 늘어난다 |
| Judge 파인튜닝(ARES) | **미채택** | 학습 데이터와 GPU가 필요하다. 범용 Judge 모델에 이진 판정 루브릭을 주는 방식을 쓴다 |
| PPI 신뢰구간(ARES) | **미채택, 기록만** | 사람 라벨 150개 이상이 필요하다. 이 프로젝트는 사람 라벨 20개로 Cohen's kappa만 보고하고, Judge 점수의 신뢰구간은 문항 bootstrap으로 낸다. 이 구간에는 Judge 자체의 오차가 들어 있지 않다(한계 절) |

검색, 생성, 운영 세 층으로 나눈다. 점수가 바뀌었을 때 어느 층에서 바뀌었는지 짚기 위해서다.

|---|---|---|---|---|---|
| 검색 | Recall@k, Precision@k, F1@k(k는 5, 10) | 규칙 | 예 | O | X |
| 검색 | MRR@10, nDCG@10 | 규칙 | 예 | O | X |
| 검색 | 검색 최고 점수 분포 | 측정 | 아니오 | O | O |
| 생성 | Citation Precision | Judge | 아니오 | O | O |
| 생성 | Refusal Accuracy | 규칙 | 예(`answerable`) | O | 거절률로 대신 표시 |
| 생성 | uv 답변 정확성 | Judge | 예(`acceptance_criteria`, `rejection_criteria`) | O | X |
| 생성 | uv 답변 품질 점수 | 규칙 항목과 Judge 항목 | 아니오 | O | O |
| 운영 | TTFT(검색 지연 별도 기록) | 측정 | 아니오 | O | O |

### 검색

검색된 청크가 관련 청크인지는 선정 실험과 같은 규칙으로 정한다. 정답 근거 구절을 60자 창(30자 간격)으로 자르고, 창 하나라도 같은 문서의 청크에 들어 있으면 그 청크는 관련 청크다. 답 없는 문항은 관련 청크가 없어 검색 지표에서 뺀다.

| 지표 | 정의 | 선정 이유 | 맹점 |
|---|---|---|---|
| Recall@k | 문항의 근거 구절 중 상위 k개 청크에서 찾은 구절의 비율 | 생성 단계에 필요한 근거가 빠졌는지 본다. 다중 문서, 요약 문항에서 중요하다 | 근거 구절을 하나만 적은 문항은 다른 곳의 같은 내용을 찾아도 놓친 것으로 센다 |
| Precision@k | 상위 k개 청크 중 관련 청크의 비율 | LLM에 넣는 문맥에 잡음이 얼마나 섞이는지 본다 | 근거가 한 구절이면 상한이 낮다(Precision@5 최대 0.2). 절대값보다 구성 간 비교에 쓴다 |
| F1@k | Recall@k와 Precision@k의 조화 평균 | 두 값을 하나로 비교할 때 | 두 맹점을 모두 물려받는다 |
| MRR@10 | 첫 관련 청크 순위의 역수 평균 | 근거가 얼마나 위에 오는지 본다 | 두 번째 이후 근거의 순위는 반영하지 않는다 |
| nDCG@10 | 관련 여부(0, 1)로 매긴 DCG를 이상적 순위의 DCG로 나눈 값 | 관련 청크가 여러 개일 때 순위 전체의 질 | 겹침이 큰 Chunking은 관련 청크 수가 늘어 값이 부푼다 |
| 검색 최고 점수 분포 | dense 최고 점수의 분포와 거절 임계값(0.6375) ± 0.05 구간에 든 질의 비율 | 정답 없이 실시간에서 볼 수 있는 검색 신호다. 이 구간에 질의가 몰리면 거절 판정이 흔들린다. 8단계에서 한국어 답 있는 문항 하나가 임계값과 0.011 차이였다 | 점수가 높아도 틀린 청크일 수 있다 |

### 생성

| 지표 | 정의 | 선정 이유 | 맹점 |
|---|---|---|---|
| Citation Precision | 답의 `[n]` 인용 중, 인용한 청크가 그 문장을 실제로 뒷받침한다고 Judge가 판정한 비율 | 출처 제시는 원문 필수 요구다. 형식만 맞춘 인용과 실제로 뒷받침하는 인용을 가른다 | 인용이 없는 문장은 보지 않는다. 거절한 답은 인용이 없어 집계에서 빠진다 |
| Refusal Accuracy | 답 없는 문항의 거절률과 답 있는 문항의 오거절률. 검색 단계 거절과 생성 단계 거절(`INSUFFICIENT_CONTEXT`)을 합해 세고 단계별로도 나눠 보고한다 | 근거가 없을 때 지어내지 않는지와, 근거가 있을 때 지나치게 거절하지 않는지를 함께 본다 | 일부만 답할 수 있는 문항은 판정이 모호하다 |
| uv 답변 정확성 | 거절하지 않은 답 중 정답인 답의 비율. 정답은 핵심 요점과 금지 내용 없음 두 항목을 모두 통과한 답이다 | 답이 맞았는지만 따로 본다. Part C에서 검색 개선이 정답률로 이어지는지 확인하는 핵심 지표다 | 요점과 금지 기준을 작성자 한 명이 쓴다. 요점을 빠뜨리면 값이 부풀려진다 |
| uv 답변 품질 점수 | 거절하지 않은 답마다 품질 6항목의 (통과 수 / 해당 항목 수)를 구해 평균한 값 | 일반 지표가 놓치는 uv 특유의 오류(명령 혼동, 식별자 철자, 낡은 동작, 근거 없는 주장)를 본다. 정답 기준 없이 판정해 Gold Set과 실시간 질의에서 같은 값으로 비교할 수 있다 | 항목 정의가 이 Corpus에 묶인다. 항목을 합친 값이라 원인은 항목별 통과율로 본다 |

- 실시간에서는 `answerable` 라벨이 없어 Refusal Accuracy 대신 거절률(검색 단계, 생성 단계)을 표시한다. 거절이 옳았는지는 Gold Set으로 판단한다.
- 거절한 답은 uv 답변 정확성과 품질 점수에서 모두 뺀다. 거절의 옳고 그름은 Refusal Accuracy만 본다. 넣으면 판정할 항목이 거의 없는 거절 답이 높은 점수를 받아 점수가 부풀려진다.

### uv 문서 루브릭

루브릭은 하나이고, 항목을 두 묶음으로 나눠 위의 두 지표를 만든다. 정답 기준이 필요한 항목은 정확성으로, 질문과 검색된 청크와 답만으로 판정하는 항목은 품질 점수로 간다.

**항목**(v1, 사용자 검수 반영)

| 지표 | 항목 | 종류 | 통과 조건 | 판정 입력 | 해당 답 |
|---|---|---|---|---|---|
| 정확성 | 핵심 요점 | Judge | `acceptance_criteria`의 요점을 모두 담았다 | 질문, 답, 정답 기준 | 거절하지 않은 답 |
| 정확성 | 금지 내용 없음 | Judge | `rejection_criteria`에 해당하는 내용이 하나도 없다 | 질문, 답, 정답 기준 | `rejection_criteria`가 있는 문항의 답 |
| 품질 | 지운 인용 없음 | 규칙 | 근거 범위 밖 인용 번호가 없다 | 답, 청크 수 | 거절하지 않은 답 |
| 품질 | 근거 없는 주장 없음 | Judge | 사실을 말하는 문장마다 `[n]` 인용이 붙어 있다 | 답 | 거절하지 않은 답 |
| 품질 | 명령, 식별자 정확성 | Judge | uv 명령과 하위 명령, 플래그, `UV_*` 환경변수, `tool.uv.*` 설정 키, 파일 이름이 검색된 청크에 있는 형태와 같다 | 답, 청크 | 명령이나 식별자가 나오는 답 |
| 품질 | 인터페이스 구분 | Judge | 프로젝트 인터페이스(`uv add`, `uv sync`, `uv lock`)와 pip 호환 인터페이스(`uv pip ...`)를 섞지 않는다 | 질문, 답 | 설치, 의존성 관련 답 |
| 품질 | 버전과 기능 상태 | Judge | 청크에 있는 preview, experimental, deprecated 표기와 버전별 차이를 전달하고, 낡은 동작을 현재 동작처럼 말하지 않는다 | 답, 청크 | 해당 기능이 나오는 답 |
| 품질 | 사전 지식 배제 | Judge | 청크에 없는 pip, poetry 같은 다른 도구의 일반 지식을 uv의 동작처럼 말하지 않는다 | 답, 청크 | 거절하지 않은 답 |

- 초안 8항목에서 "인용 정합성"은 Citation Precision과, "거절 적절성"은 Refusal Accuracy와 같은 것을 재서 뺐다.
- 형식 준수(유효한 `[n]` 인용 하나 이상)는 뺐다. 사실 문장마다 인용을 요구하는 "근거 없는 주장 없음"을 통과하면 형식 준수도 늘 통과해 품질 점수에 정보를 더하지 않는다. 9단계 LLM 선정에서 쓴 형식 준수율은 그 실험의 기록으로만 남는다.
- "명령, 식별자 정확성"은 문서 전체가 아니라 검색된 청크와 대조한다. 이 서비스는 근거로 준 청크 안에서만 답해야 하므로, 사전 지식으로 맞는 식별자를 써도 청크에 없으면 실패다. 검색이 근거를 놓치면 이 항목도 함께 떨어지므로, 원인은 검색 지표와 함께 보고 가린다.
- "금지 내용 없음"은 test set에 새로 둔 `rejection_criteria`를 쓴다. 요점을 다 담고도 틀린 말을 덧붙인 답을 잡는다. `rejection_criteria`가 빈 문항은 이 항목이 해당 없음이고 핵심 요점만으로 정답을 정한다.
- "근거 없는 주장 없음"은 Faithfulness를 두지 않아 생긴 빈틈(인용 없이 지어낸 문장)을 일부 메운다.
- 핵심 요점은 요점을 모두 담아야 통과다. 요점별 통과율(담은 요점 수 / 전체 요점 수)은 따로 보고해 부분 정답의 정도를 본다.

**항목 상세**

Judge와 사람 라벨러가 같은 기준으로 판정하도록 항목마다 판정 질문, 해당 없음 조건, 통과와 실패 예시를 정한다. 예시는 test set 문항에서 가져왔다. Judge 프롬프트는 이 절을 그대로 옮겨 만든다.

공통 규칙:

- 답이 한국어여도 의미로 판정한다. 기준이 영어라는 이유로 실패 처리하지 않는다.
- 같은 내용을 다르게 표현한 것은 통과다. 명령, 플래그, 환경변수, 설정 키, 파일 이름은 예외로 글자 그대로 같아야 한다.
- Judge 항목의 "해당 없음"은 아래 조건에 맞을 때만 고를 수 있다. 조건에 맞지 않는데 해당 없음을 내면 파싱 실패와 같이 `judge_failed`로 처리한다.

| 항목 | 판정 질문 | 해당 없음 | 통과 예 | 실패 예 |
|---|---|---|---|---|
| 핵심 요점 | 요점마다 "이 요점의 내용이 답에 들어 있는가". 모든 요점이 예이면 통과 | 없음 | `test-factual-07`에서 `--require-build-hashes`를 답하고 전이 의존성까지 적용된다고 말함 | 같은 문항에서 플래그만 답하고 전이 의존성 범위를 빠뜨림 |
| 금지 내용 없음 | 금지 기준마다 "답이 이 내용을 사실로 말하는가". 하나라도 예이면 실패. 금지 내용을 부정하거나 틀렸다고 설명하는 것은 통과 | `rejection_criteria`가 빈 문항 | `test-trap-04`에서 기존 `tool.uv.dev-dependencies`에 기록된다고 답함 | 같은 문항에서 "`uv add --dev`는 `[dependency-groups]`에 기록한다"고 답함 |
| 지운 인용 없음 | (규칙) 근거 수를 넘는 번호의 인용이 없는가 | 없음 | 근거 5개에 `[1]`, `[3]`만 씀 | 근거 5개인데 `[7]`을 씀 |
| 근거 없는 주장 없음 | "uv의 동작, 기본값, 명령, 설정을 말하는 문장 중 `[n]` 인용이 없는 문장이 있는가". 있으면 실패. 질문을 다시 말하는 문장, 문장을 잇는 말, 바로 앞뒤 문장의 인용을 받는 코드 블록은 세지 않는다 | 없음 | 사실 문장마다 인용이 붙고, 마무리 "이렇게 설정하면 됩니다"만 인용이 없음 | 인용 붙은 설명 뒤에 "이 설정은 Windows에서도 같다"를 인용 없이 덧붙임 |
| 명령, 식별자 정확성 | "답에 나온 uv 명령, 하위 명령, 플래그, `UV_*` 환경변수, `tool.uv.*` 설정 키, 파일 이름이 모두 검색된 청크에 같은 형태로 있는가". 하나라도 청크에 없거나 철자가 다르면 실패 | 답에 그런 식별자가 하나도 없음 | `test-factual-08`에서 청크에 있는 `uv python dir`을 답함 | `uv python dirs`, `UV_PYTHON_DIR`처럼 청크에 없는 형태를 씀 |
| 인터페이스 구분 | "프로젝트 인터페이스(`uv add`, `uv remove`, `uv sync`, `uv lock`, `uv run`)와 pip 호환 인터페이스(`uv pip ...`)를 섞어, 한쪽의 동작을 다른 쪽 명령으로 하라고 안내하는가". 섞으면 실패 | 답에 설치, 의존성 명령이 하나도 없음 | 프로젝트에 의존성을 더하려면 `uv add`를 쓰라고 답함 | "프로젝트 의존성에 추가하려면 `uv pip install requests`를 실행하세요" |
| 버전과 기능 상태 | "검색된 청크가 답에 쓴 기능을 preview, experimental, deprecated로 표시하거나 버전 조건을 달았을 때, 답이 그 표시를 전달하는가. 그리고 청크가 낡았다고 한 동작을 현재 동작처럼 말하지 않는가" | 답에 쓴 기능에 청크가 그런 표시나 버전 조건을 달지 않음 | `test-multi_doc-06`에서 `--default`가 experimental이라고 함께 말함 | 같은 문항에서 `uv python install --default`를 표시 없이 권함 |
| 사전 지식 배제 | "청크에 없는 다른 도구(pip, poetry, pipenv, conda 등)의 동작이나 명령을 uv의 동작처럼 말하는가". 말하면 실패. 다른 도구와의 비교를 청크가 직접 다루면 통과 | 없음 | 청크에 있는 `uv pip` 호환성 차이만 설명함 | "uv도 pip처럼 `--user`로 사용자 영역에 설치합니다"를 근거 없이 말함 |

**품질 점수 계산**

- 각 항목은 답마다 통과, 실패, 해당 없음 중 하나로 판정한다. 규칙 항목은 코드로 계산하고 Judge에 맡기지 않는다.
- 답 점수는 (통과 항목 수 / 해당 항목 수)이고, 품질 점수는 답 점수의 평균이다. 가중치는 동일하게 두고, test set 결과를 보기 전에 정한 값을 바꾸지 않는다.
- 품질 점수와 함께 규칙 소계, Judge 소계, 항목별 통과율을 항상 보고한다.

**검증 조건**(통과하지 못한 항목은 해당 지표에서 빼고 참고값으로만 보고한다)

| 조건 | 기준 |
|---|---|
| 반응성 | 일부러 망가뜨린 시스템(아래 타당성 검증)에서 해당 항목 통과율이 떨어진다 |
| 변별력 | 통과율이 test set 전체에서 1.0이거나 0.0이 아니다. 9단계에서 지운 인용 비율이 0.000이었으므로 규칙 항목(지운 인용 없음)은 이 조건에서 빠질 수 있다 |
| 신뢰성(Judge 항목) | 3회 반복 판정 일치율 0.90 이상, 사람 라벨 대비 Cohen's kappa 0.60 이상 |
| 중복성 | 다른 항목과 답별 값의 상관이 0.95 미만이다 |

정확성과 품질 점수 자체도 아래 망가뜨린 시스템에서 떨어져야 한다. 품질 점수가 떨어지지 않으면 다른 항목이 그 변화를 가린 것으로 보고 구성을 다시 본다.

### 운영

평가는 스트리밍 경로(`answer_stream`)로 돌려 같은 호출에서 아래 값을 모두 잰다.

| 지표 | 정의 | 선정 이유 |
|---|---|---|
| 검색 지연 | 질의 임베딩과 Qdrant 조회에 걸린 시간 | TTFT가 늘었을 때 검색과 LLM 중 어디서 늘었는지 가른다 |
| TTFT | 요청을 받은 시점부터 첫 답변 토큰을 보낼 때까지 | 사용자가 느끼는 첫 응답 속도. 검색 지연이 포함된다 |
| TPOT | (Latency − TTFT) / (출력 토큰 수 − 1) | 스트리밍 중 토큰이 나오는 속도 |
| Latency | 요청을 받은 시점부터 스트리밍 마지막 이벤트를 보낼 때까지 실제로 잰 시간 | 전체 소요 시간. 공식으로 계산하지 않고 실측하며, 검색 지연 + LLM TTFT + TPOT × (출력 토큰 − 1) 분해는 원인을 볼 때만 쓴다 |
| 질의당 비용 | 입력, 출력 토큰 수 × 단가. 검색 단계 거절(0원)을 포함한 평균 | 엘리스 Serverless는 토큰으로 과금한다. 비용은 처리 속도가 아니라 이 값이 정한다 |

- 검색 단계에서 거절한 질의는 출력 토큰이 0이라 TPOT가 없다. TPOT 집계에서 빼고, 거절 질의의 Latency는 따로 집계한다.
- 동시 처리량(Throughput)은 재지 않는다(한계 절).

## Judge

### 호출 구성

| 호출 | 판정 항목 | Gold Set | 실시간 |
|---|---|---|---|
| 인용 대조 | Citation Precision(인용별) | O | O |
| 루브릭 | 정확성 2항목, 품질 Judge 5항목 | O(7항목) | O(품질 5항목) |

- 답 하나에 Judge 2회다. 검색 단계에서 거절한 답은 LLM 답이 없어 Judge를 부르지 않는다.
- Judge 모델은 gemini-3.8-flash다. 답변 모델(claude-haiku-5-5)과 계열이 달라 자기 선호 편향을 줄인다.
- 판정은 모두 이진이다. 점수를 직접 매기게 하면 호출마다 척도가 흔들려, 이진 판정을 모아 비율로 만든다.
- 출력은 JSON Schema로 받고 pydantic으로 엄격하게 파싱한다. 파싱에 실패한 판정은 `judge_failed`로 기록하고 집계에서 빼며, 실패율을 따로 보고한다.
- 질문, 답, 근거는 모두 신뢰하지 않는 입력이다. 경계 태그를 중화하고, 태그 안의 지시를 따르지 말라고 Judge 프롬프트에 명시한다.

### 신뢰성, 일관성, Human Alignment

| 확보할 것 | 방법 | 기준 |
|---|---|---|
| 신뢰성(Judge가 재려는 것을 재는가) | 일부러 망가뜨린 시스템에서 Judge 지표가 떨어지는지 확인(타당성 검증) | 정상 대비 짝지은 차이 95% 구간이 0을 포함하지 않음 |
| 일관성 | 같은 입력으로 3회 판정해 일치율을 잰다. Gold Set 평가는 3회 다수결로 확정한다 | 항목별 일치율 0.90 이상 |
| Human Alignment | 답변 20건을 사람이 같은 루브릭으로 라벨링하고 Judge와 비교 | 항목별 Cohen's kappa 0.60 이상 |

- 기준에 못 미치는 항목은 루브릭 문구를 고쳐 한 번 다시 잰다. 그래도 못 미치면 해당 지표에서 빼고 참고값으로만 보고한다.
- Judge 프롬프트와 루브릭은 버전 파일로 두고 해시를 결과에 기록한다.
- 실시간 대시보드에는 기준을 통과한 항목만 올린다. 검증하지 않은 Judge 점수가 실시간으로 쌓이면 틀린 숫자가 쌓인다.

## 재현성

### 단일 명령

`make eval CONFIG=configs/baseline.toml` 하나가 test set 전체(영어, 한국어)에 대해 검색, 답변 생성, 규칙 지표, Judge 지표, 운영 지표를 모두 계산하고 `reports/<run_id>/`에 문항별 결과(`results.jsonl`)와 요약 Report(`summary.md`)를 쓴다. 설정 파일은 표준 라이브러리(`tomllib`)로 읽을 수 있는 TOML이다. Judge 일치도 검증(`make agreement`)은 평가와 별도 명령이다.

### 기록 항목

| 항목 | 값 |
|---|---|
| 코드 | git commit hash |
| 데이터 | corpus manifest 해시, gold set 파일 해시 |
| 인덱스 | 인덱스 계약(임베딩 모델, 토크나이저, Chunk 설정 해시) |
| 모델 | 요청한 모델 이름과 응답의 `model` 필드(실제로 응답한 버전) |
| 생성 조건 | temperature, 출력 상한, 프롬프트 해시, Judge 프롬프트와 루브릭 해시 |
| seed | 문항 표집 seed(2026), bootstrap seed(2026), LLM seed(`null`, 사유 함께 기록) |
| 설정 | 설정 파일 전체 |

### seed를 고정할 수 없는 문제

답변 모델과 Judge 모델 모두 게이트웨이가 `seed`를 거부(400)한다. 그래서 LLM 출력의 재현은 seed가 아니라 다음 세 가지로 확보한다.

- temperature를 0으로 고정한다.
- 답변 생성은 평가 기록 저장소(PostgreSQL)가 캐시 역할을 한다. run_id는 설정, Gold 파일, 원문, 인덱스 계약, 답변 모델, 프롬프트 해시로 정해지고(git commit은 기록만 한다), 같은 run_id로 다시 돌리면 이미 기록된 문항은 LLM을 부르지 않아 같은 Report가 나오고 비용은 0이다. 중간에 실패한 문항만 다음 실행에서 다시 부른다.
- Judge 응답은 요청 해시(모델, 메시지, temperature, 출력 상한) 키로 `LlmCache`에 저장해 같은 판정 요청을 다시 부르지 않는다.
- Judge는 3회 판정 다수결로 확정하고 3회 일치율을 보고해, 캐시 없이 새로 돌렸을 때 얼마나 흔들리는지를 수치로 남긴다.

## 실시간 누적 평가

### 무엇을 보여주나

실제 사용자 질의가 들어올 때마다 위 표의 실시간 지표가 쌓이고, 지표마다 다음 세 값을 질의 순서에 따라 그린다.

- **누적 평균과 95% 구간**: 비율 지표는 Wilson 구간, 지연과 비용은 bootstrap 구간. 질의가 적을 때는 구간이 넓게 그려져, 초반의 흔들림을 실제 변화로 오해하지 않게 한다.
- **최근 50건 이동 창**: 누적 평균은 시간이 갈수록 움직이지 않으므로, 최근 변화는 이동 창으로 본다.
- **Gold Set 기준선**: 같은 구성(`config_id`)의 최신 Gold Set 평가값을 수평선으로 겹친다.

### 기록 단위와 키

- 질의 하나가 기록 하나다. 키는 요청 id(`X-Request-ID`, 없으면 서버가 만든 값)이고 저장소에서 UNIQUE다. 같은 요청을 다시 보내도 기록이 늘지 않는다.
- Judge 판정은 (기록 id, 지표, Judge 모델, 프롬프트 버전)이 키다. Judge를 다시 돌리면 같은 행을 덮어쓴다.
- 모든 기록에 `config_id`(인덱스 계약 해시, 프롬프트 버전, 답변 모델)를 붙인다. Part C에서 Hybrid로 바꾸면 구성별로 선이 갈린다.
- Gold Set 평가 결과도 같은 저장소에 `source=gold`로 넣는다.

### 응답을 막지 않는다

- 기록 저장은 응답을 보낸 뒤에 한다. 저장에 실패해도 응답은 나가고, 실패는 로그로만 남는다.
- Judge는 백그라운드 작업이 큐에서 꺼내 채점한다. 즉시 지표(거절률, 지연, 비용, 검색 점수)는 응답 직후, Judge 지표는 몇 초 뒤에 반영된다.
- 서버가 재시작하면 채점이 안 된 기록을 저장소에서 다시 꺼낸다. 중간에 죽어도 다시 띄우면 이어서 채점한다.

### 비용 상한

- 실시간 Judge는 질의 1건에 2회 호출이다. 입력 3천 토큰, 출력 300토큰으로 가정하면 약 ₩10이다(추정, 파일럿에서 실측해 갱신).
- 샘플링 비율(`JUDGE_SAMPLE_RATE`, 기본 1.0)과 예산 상한(`JUDGE_BUDGET_KRW`, 기본 ₩3,000)을 둔다. 예산을 넘으면 채점을 멈추고 대시보드에 표시한다. 즉시 지표는 예산과 상관없이 계속 쌓인다.

### 실시간 지표로 말할 수 없는 것

- 답이 맞았는지(uv 답변 정확성)는 모른다. 인용이 맞고 형식을 지킨 오답은 실시간 지표에 드러나지 않는다.
- 거절이 옳았는지 모른다. 실시간에서는 거절률만 보고, 거절의 정오는 Gold Set으로 판단한다.
- 실시간 질의의 분포는 Gold Set과 다르다. 두 값의 차이는 시스템 변화와 질의 분포 변화가 섞인 값이다.

## Gold Set: test set 설계

### 구성

| 유형 | 문항 | 비중 | 목적 |
|---|---|---|---|
| factual | 12 | 30% | 검색과 인용 정확도 |
| multi_doc | 10 | 25% | 여러 문서 종합. 그중 4문항 이상은 추론 문항 |
| summary | 6 | 15% | 원문 요구인 생성형 질의 |
| unanswerable | 8 | 20% | 거절 로직과 Hallucination |
| trap | 4 | 10% | 유사 용어, 버전 혼동으로 사전 지식에 끌려가는지 |
| 합계 | 40 | | |

- 영어 정본 40문항과 한국어 번역 40문항. 번역 방식은 dev set과 같다(`make gold-translate`).
- 생성형 질의는 요약 6문항과 추론 문항 4문항 이상이다. 추론 문항은 문서에 그대로 적힌 답이 없고, 두 문서 이상의 조건을 결합하거나 비교해야 답이 나오는 질문이다(예: 설정 A와 플래그 B를 함께 쓰면 어느 쪽이 우선하는가).
- 답 없는 문항은 dev set의 교훈대로 근접 주제(문서에 비슷한 구절이 있어 오답을 유도하는 질문)를 절반 이상 둔다.

### 필드

dev set 스키마(`app/schema/gold_schema.py`)에 아래를 더한다. 스키마 변경은 Gold Set PR에서 한다.

| 필드 | 내용 |
|---|---|
| `acceptance_criteria` | 모든 문항에 채운다. 답 있는 문항은 답이 반드시 담아야 할 요점 목록이고 요점 하나가 Judge 이진 판정 하나가 된다. 답 없는 문항은 "근거가 없다고 밝히고 답을 지어내지 않는다" 한 줄이다 |
| `rejection_criteria` | 답에 들어가면 안 되는 내용(trap 문항의 낡은 동작, pip 동작을 uv 동작처럼 말하기, 답 없는 문항에서 지어낸 값) |
| `requires_reasoning` | 추론 문항 여부. 유형별 값과 별도로 추론 문항의 값을 보고한다 |

### 구축 방법

1. `make gold-draft SPLIT=test`로 영어 초안을 만든다. 원문 표집, 근거 인용 검증, 재시도 규칙은 dev set과 같다.
2. 초안 40문항을 모두 읽고, 변별력이 없는 문항(문서 없이도 아는 내용)은 교체하고, 추론 문항을 직접 작성하고, `acceptance_criteria`와 `rejection_criteria`를 채운다.
3. 사용자가 전 문항을 검수한다.
4. `make gold-translate SPLIT=test`로 한국어 묶음을 만들고 원문과 나란히 검수한다.
5. `make gold-check`로 스키마, id 중복, 근거 일치, 번역 짝, dev set과의 분리를 검사한다.

### dev set과 분리 규칙

- 근거 구절을 공유하는 문항이 없어야 한다. test 근거 구절의 60자 창 하나라도 dev 근거 구절 안에 있으면 실패다. 검색 판정과 같은 창 규칙이다.
- 같은 문서에서 근거를 뽑는 것은 허용한다. 81개 문서 중 근거가 걸린 문서가 dev에서 이미 38개라, 문서를 완전히 분리하면 test 표집 대상이 너무 줄어든다.
- 선정 실험(1~9단계)에는 test set을 쓰지 않았다. test set은 10, 11단계와 Part C에서만 쓴다.

### 편향과 한계

- 초안을 LLM(`gpt-6.1-terra`)이 만든다. LLM 초안은 근거가 한 구절 안에 들어가는 질문으로 쏠린다. dev set의 factual 12문항이 모두 근거 1개였다. 추론 문항을 직접 작성하는 것은 이 쏠림을 줄이기 위해서다.
- 질문, 기준, 검수를 작성자 한 명이 한다. 질문 문체가 단조롭고, 기준에서 요점을 빠뜨리면 uv 답변 정확성이 부풀려진다.
- 원문 표집은 1,500자 이상 문서만 대상으로 한다. 짧은 안내 페이지에 대한 질문은 없다.
- Corpus에는 CLI 레퍼런스와 환경변수 레퍼런스 페이지가 없다. 식별자 질문은 개념 문서 본문에 나오는 식별자로만 만든다.
- 한국어 묶음은 질문만 번역하고 정답과 기준은 영어다. Judge는 한국어 답을 영어 기준과 대조한다.
- 40문항이라 유형별로는 4~12문항이다. 유형별 값은 신뢰구간이 넓어 경향으로만 읽는다.

## 파일럿

기준선 실행(`baseline-4e6abaee3113`)에서 답한 기록 앞 10개를 3회씩 판정했다(`make eval EVAL_ARGS="--judge-limit 10"`, Judge 호출 60회, 약 ₩460).

| 발견 | 조치 |
|---|---|
| 인용이 많은 긴 답(인용 19개, 11개) 2건의 인용 판정이 3회 모두 JSON 도중에 끊겼다. 추론 토큰과 줄바꿈 많은 JSON이 출력 상한(1,500)을 다 썼다 | 인용을 8개씩 나눠 부르고 출력 상한을 게이트웨이 상한(2,000)으로 올렸다. 다시 판정해 10건 모두 통과 |
| "인터페이스 구분", "버전과 기능 상태"가 해당 사항이 없을 때 표본마다 `na`와 `pass`를 오갔다. `na`는 품질 점수 분모에서 빠져 같은 답의 점수가 표본마다 달랐다(0.83과 1.0) | 프롬프트 v2: 해당 사항이 없으면 `pass`가 아니라 `na`라고 명시(식별자 정확성도 같은 문구). 같은 10건의 3회 일치가 두 항목 모두 9/10에서 10/10 |
| 답한 59건 중 8건(14%)이 생성 출력 상한(1,500토큰)에 걸려 문장 중간에 잘렸다. 한국어 요약, 다중 문서 문항이 대부분이다 | 사용자 결정: 기준선은 그대로 재고 결함으로 기록한다. 출력 상한 조정은 별도 변경으로 비교한다 |
| 핵심 요점을 놓친 답 3건은 판정 이유를 읽어 보니 모두 실제로 놓친 경우였다(검색이 근거를 못 가져온 2건, 답이 잘린 1건) | 없음 |

v1과 v2의 판정은 프롬프트 버전(`v1-8e3e33b46f92`, `v2-885fe14db546`)으로 저장소에 따로 남는다. 이후 결과는 모두 v2다.

## 통과 기준(실험 전에 정함)

### 지표 타당성 검증

의도적으로 망가뜨린 시스템에서 지표가 떨어지지 않으면, 그 지표는 측정하려는 것을 재지 못하는 것으로 본다.

| 망가뜨리는 방법 | 떨어져야 하는 지표 | 통과 조건 |
|---|---|---|
| 검색 결과를 무작위 청크 5개로 교체 | Recall@5, uv 답변 정확성, uv 답변 품질 점수(사전 지식 배제, 명령과 식별자 정확성) | 정상 대비 짝지은 차이 95% 구간이 0을 포함하지 않음 |
| 거절 판정 끄기(임계값 0, 근거 부족 토큰 무시) | Refusal Accuracy(답 없는 문항 거절률), uv 답변 품질 점수(근거 없는 주장 없음) | 같음 |
| 인용 번호를 무작위로 섞기 | Citation Precision | 같음 |

떨어지지 않는 지표는 정의나 Judge 프롬프트를 고쳐 한 번 다시 재고, 그래도 떨어지지 않으면 최종 지표에서 뺀다.

검증 방식(구현하면서 정함): 변형은 영어 40문항만, Judge 1회로 돌리고, 기준선은 같은 문항의 첫 표본만 써서 표본 수를 맞춘다. 거절을 끈 변형의 "근거 없는 주장 없음"은 짝지을 수 없다. 기준선에서 답 없는 문항은 모두 거절돼 판정할 답이 없기 때문이다. 그래서 이 변형은 답 없는 문항 거절률만 판정하고, 새로 답한 답의 품질은 참고값으로 남긴다(계획과 달라진 점).

## 타당성 검증 결과

`make validity`. 변형은 영어 40문항, Judge 1회이고, 기준선(`baseline-4e6abaee3113`)의 같은 문항 첫 표본과 짝지었다. 차이는 기준선 - 변형이고 구간은 bootstrap 95%다.

| 변형 | 떨어져야 하는 지표 | 짝 | 차이 [95% 구간] | 판정 |
|---|---|---|---|---|
| 무작위 청크 | Recall@5 | 32 | 0.773 [0.648, 0.891] | 통과 |
| 무작위 청크 | 정답률(답 있는 문항에서 답했고 정답) | 32 | 0.719 [0.563, 0.875] | 통과 |
| 거절 끔 | 답 없는 문항 거절률 | 8 | 1.000 [1.000, 1.000] | 통과 |
| 인용 섞기 | Citation Precision | 30 | 0.879 [0.780, 0.952] | 통과 |
| 근거 바꿔치기 | uv 답변 품질 점수 | 30 | 0.188 [0.133, 0.242] | 통과 |
| 근거 바꿔치기 | Citation Precision | 30 | 0.970 [0.941, 0.993] | 통과 |

계획과 달라진 점: 사전 규칙은 무작위 청크 변형에서 품질 점수도 떨어져야 한다고 정했다. 무작위 청크를 받은 답변 모델이 40문항 중 38문항을 거절해 품질 점수를 짝지을 답이 2개뿐이었다. 측정 설계가 이 경우를 다루지 못한 것이라, 실제 답은 그대로 두고 Judge에게만 무작위 청크를 근거로 보여 주는 변형(근거 바꿔치기)을 더해 품질 점수와 Citation Precision이 근거를 실제로 읽는지 확인했다.

항목별로 보면 근거 바꿔치기에서 "명령, 식별자 정확성"이 1.000에서 0.043, "근거 없는 주장 없음"이 0.806에서 0.667로 떨어졌다. "사전 지식 배제"는 1.000 그대로였다. 답에 다른 도구의 동작이 없으면 근거가 바뀌어도 통과가 맞는 항목이라, 이 변형으로는 반응성을 확인할 수 없다. 정답률은 0.031 차이로 거의 그대로다. 정확성은 근거가 아니라 정답 기준과 대조하므로 의도대로다.

변별력 조건 점검: 기준선에서 품질 6항목 중 "지운 인용 없음", "명령, 식별자 정확성", "인터페이스 구분", "버전과 기능 상태", "사전 지식 배제" 5항목의 통과율이 두 언어 모두 1.000이다. 사전 규칙대로면 이 항목은 품질 점수에서 빠진다. 사람 라벨 대비 kappa와 함께 최종 구성을 정한다.

## 한계

- Faithfulness를 두지 않았다. 인용 없는 문장은 품질 점수의 "근거 없는 주장 없음"이 답 단위로 통과, 실패만 잡고, 답 안에서 지어낸 주장이 몇 개인지는 재지 않는다.
- 동시 처리량(Throughput)을 재지 않았다. 동시 사용자 수용량은 `LlmGate` 동시 호출 상한과 CPU 임베딩이 정하며, 이 값은 측정 없이 설정값으로만 남는다.
- 사람 라벨이 20건이라 Judge 오차를 지표 값에 반영해 보정하지 못한다. 보고하는 신뢰구간은 문항 표집의 불확실성만 담는다.
- 실시간 Judge는 1회 판정이라 Gold Set의 3회 다수결보다 흔들린다.
- LLM seed를 고정할 수 없다. 캐시가 없는 새 환경에서 다시 돌리면 생성과 Judge 결과가 일부 달라질 수 있다.
