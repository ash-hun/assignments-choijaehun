RAG QA 서비스의 구성 요소를 하나씩 고정해 가며 고른 과정이다. 앞 단계에서 정한 값을 다음 단계의 고정 변인으로 쓰므로, 아래 순서대로 읽으면 결정이 쌓이는 과정을 따라갈 수 있다.

1~9단계는 dev set으로 구성 요소를 **고르는** 실험이고, 10, 11단계는 고른 구성의 성능을 test set으로 **재는** 실험이다. 10, 11단계의 측정 방식은 Part C(개선 실험)의 기준선과 개선안 비교에도 그대로 쓴다.

## 모든 실험에 공통인 규칙

- **선정에는 dev set만 쓴다.** 최종 평가용 test set과 분리해, 같은 문항으로 고르고 평가해서 점수가 부풀려지는 것을 막는다.
- **판정 규칙은 실험 전에 정한다.** 실험 계획(`project_planning/plan.md`)에 단계마다 주 지표와 판정 순서를 먼저 적었다. 결과를 본 뒤 규칙을 바꾼 경우는 각 문서의 "계획과 달라진 점"에 이유와 함께 남겼다.
- **차이는 신뢰구간으로 판정한다.** 문항을 복원 추출하는 bootstrap 2,000회(seed 2026)로 95% 구간을 구한다. 두 후보는 같은 문항끼리 짝지은 점수 차이의 구간으로 비교하고, 구간이 0을 포함하면 차이가 없다고 본다. 차이가 없으면 미리 정한 다음 기준(단순성, 비용 등)으로 가른다.
- **검색 정확도는 근거 단위로 잰다.** 검색된 청크에 정답 근거 구절이 들어 있는지로 판정한다. 구절을 60자 창으로 잘라(30자 간격) 창 하나라도 같은 문서의 청크에 있으면 찾은 것으로 본다. 주 지표는 Hit@5(상위 5개 안에 근거가 있는 문항 비율)와 MRR@10이다.
- **영어와 한국어 질의를 모두 본다.** Corpus는 영어이고, 한국어 사용자 질의를 다루기 위해 dev set에 한국어 번역 묶음을 두었다.
- **재현 가능하게 남긴다.** 모든 실험은 Docker Compose 위에서 `make` 명령 하나로 다시 돌릴 수 있고, 원자료는 `research/artifacts/`에 있다. 각 문서 끝에 재현 명령을 적었다.

## 성능 평가 실험 설계(10, 11단계)

### 10. 검색 성능 평가

검색 실패와 생성 실패를 나눠 보기 위해 검색만 따로 잰다. 관련 청크의 판정은 선정 실험과 같다. 정답 근거 구절의 60자 창 하나라도 같은 문서의 청크에 들어 있으면 그 청크는 관련 청크다.

| 지표 | 정의 | 보는 것 |
|---|---|---|
| Recall@k | 문항의 근거 구절 중 상위 k개 청크에서 찾은 구절의 비율 | 필요한 근거를 빠뜨리지 않는가. 다중 문서, 요약 문항에서 중요하다 |
| Precision@k | 상위 k개 청크 중 관련 청크의 비율 | LLM에 넣는 문맥에 잡음이 얼마나 섞이는가 |
| F1@k | Recall@k와 Precision@k의 조화 평균 | 두 값을 하나로 비교할 때 |
| MRR@10 | 첫 관련 청크 순위의 역수 평균 | 근거가 얼마나 위에 오는가 |
| nDCG@10 | 관련 여부(0, 1)로 매긴 DCG를 이상적인 순위의 DCG로 나눈 값. 이상적인 순위는 인덱스 전체의 관련 청크 수(최대 10개)로 만든다 | 관련 청크가 여러 개일 때 순위 전체의 질 |

- k는 5와 10이다. 5는 생성 단계에 넣는 문맥 수의 기준이고, 10은 재순위화 여지를 본다.
- 답 없는 문항은 관련 청크가 없어 검색 지표에서 뺀다. 이 문항은 11단계의 거절 판정에서 본다.
- 영어와 한국어 질의를 따로 보고하고, 문항 유형별(사실, 다중 문서, 요약, 함정) 값도 함께 낸다.
- 신뢰구간과 비교 방법은 공통 규칙(bootstrap, 짝지은 차이)을 따른다.
- 주의: Precision@k는 근거가 한 구절뿐인 문항에서 상한이 낮다(관련 청크가 1개면 Precision@5는 최대 0.2). 그래서 절대값보다 구성 간 비교에 쓴다. 겹침이 큰 Chunking은 한 구절이 여러 청크에 걸쳐 관련 청크 수가 늘어나므로, 겹침이 다른 구성끼리 Precision과 nDCG를 비교할 때는 이 점을 함께 적는다.

### 11. 생성 성능 평가

확정 지표는 Citation Precision, Refusal Accuracy, uv 문서 루브릭 통합 점수(규칙 항목과 Judge 항목, 핵심 요점이 Answer Correctness), 운영 지표(TTFT, TPOT, Latency, 질의당 비용)다. 정의, 선정 이유, 통과 기준은 [research/gold_metric_selection.md](../../research/gold_metric_selection.md). 아래 루브릭은 초안이고 항목은 별도 설계로 확정한다. 일반 지표는 "근거에 충실한가"를 보지만, uv 문서에서 실제로 틀리기 쉬운 지점(명령 혼동, 식별자 철자, 낡은 동작)은 따로 보지 않으면 놓친다.

**uv 문서 루브릭(초안)**

| 항목 | 통과 조건 | 해당 문항 |
|---|---|---|
| 핵심 요점 | 문항의 `acceptance_criteria` 요점을 모두 담았다 | 답 있는 문항 |
| 명령 정확성 | 답에 나온 uv 명령과 하위 명령이 문서에 있는 형태다 | 명령이 나오는 답 |
| 식별자 정확성 | 플래그, 환경변수(`UV_*`), 설정 키(`tool.uv.*`), 파일 이름(`uv.lock`, `pyproject.toml`)의 철자가 문서와 같다 | 식별자가 나오는 답 |
| 인터페이스 구분 | 프로젝트 인터페이스(`uv add`, `uv sync`, `uv lock`)와 pip 호환 인터페이스(`uv pip ...`)를 섞지 않는다 | 설치, 의존성 관련 문항 |
| 버전과 기능 상태 | preview, experimental, deprecated 표기와 버전별 차이를 전달하고, 낡은 동작을 현재 동작처럼 말하지 않는다 | 함정 문항, 버전 관련 문항 |
| 사전 지식 배제 | pip, poetry 같은 다른 도구의 일반 지식을 uv의 동작처럼 말하지 않는다 | 모든 답 |
| 인용 정합성 | `[n]` 인용이 붙은 문장마다 해당 청크가 그 내용을 뒷받침한다 | 인용이 있는 답 |
| 거절 적절성 | 답 없는 문항에서는 지어내지 않고 근거가 없다고 밝힌다. 답 있는 문항에서는 거절하지 않는다 | 모든 문항 |

- 항목마다 통과, 실패, 해당 없음 중 하나로 판정하고, 문항 점수는 (통과 수 / 해당 항목 수)다. 점수를 직접 매기게 하면 Judge마다 척도가 달라져, 계획서의 원칙대로 이진 판정을 모아 점수를 만든다.
- Judge는 생성 모델과 다른 계열을 쓴다. 같은 입력으로 3회 판정해 다수결로 정하고, 3회 일치율을 함께 보고한다.
- 사람 라벨 20건으로 Judge와의 일치율과 Cohen's kappa를 잰다. 일치율이 낮은 항목은 루브릭 문구를 고치고 다시 잰다.
- 루브릭과 Judge 프롬프트는 버전 파일로 두고 해시를 결과에 기록한다.
- 타당성 검증: 검색 결과를 무작위 청크로 바꾸거나 거절 로직을 끈 시스템에서 해당 항목 점수가 실제로 떨어지는지 확인한다. 떨어지지 않는 항목은 측정하려는 것을 재지 못하는 것으로 보고 다시 설계한다.
