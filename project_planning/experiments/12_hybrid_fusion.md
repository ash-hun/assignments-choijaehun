# 12. 검색 융합 방식 비교(Part C 개선 실험)

**결론: 서비스 검색을 질의 언어에 따라 고르도록 바꾼다. 영어 질의는 Hybrid-CC, 한국어 질의는 Dense(`RETRIEVAL_MODE=routed`).** 사전 판정 규칙(영어와 한국어를 합친 Recall@5)으로는 세 조건 모두 Dense 대비 판정 불가였다. 언어별로 나누면 영어는 BM25를 섞은 세 조건 모두 오르고 한국어는 모두 내려가 합계에서 상쇄됐다. 결과를 본 뒤 서비스 범위가 영어 질의 기본(한국어는 추가 확인)임을 확인했고, 이 결정에 쓰지 않은 dev set에서 같은 양상을 확인한 뒤 언어별 선택을 채택했다. 사전 규칙과 다르게 정한 근거는 "결정" 절에 있다.

가설, 조건, 판정 규칙은 실행 전에 이 문서에 적어 커밋(`ed8cf07`)했고, 세 조건의 실행은 모두 그 커밋에서 돌렸다. 결과를 본 뒤 추가한 분석은 "사후 탐색"으로 표시하고 판정에 쓰지 않았다.

## 질문

dense 검색에 BM25를 섞으면 기준선이 놓친 근거를 찾는가. 섞는 방식이 순위만 쓰는 RRF인지, 점수 크기를 쓰는 Convex Combination(CC)인지에 따라 결과가 달라지는가.

## 가설

| 가설 | 내용 | 근거 |
|---|---|---|
| H0 | BM25 단독은 전체 Recall@5가 Dense보다 낮다. 영어 trap에서는 Dense 이상이다. 한국어에서는 Dense보다 크게 낮다 | BM25는 단어가 같아야 맞는다. trap은 버전, 식별자 같은 정확한 문자열이 답을 가른다. Corpus는 영어라 한국어 질문은 영문 식별자 외에 맞는 단어가 거의 없다 |
| H1 | Hybrid-RRF와 Hybrid-CC 모두 Dense보다 Recall@5가 높다 | 두 주제가 섞인 질문에서 dense 질의 벡터는 한쪽으로 기울고, BM25는 두 주제의 단어를 각각 맞춘다 |
| H2 | 기본값끼리 비교하면 Hybrid-CC가 Hybrid-RRF보다 Recall@5가 높다 | RRF는 순위만 써서, 1위와 2위의 점수 차가 커도 한 칸 차이로 본다. CC는 점수 차를 쓴다 |
| H3 | 한국어에서는 Hybrid의 Recall@5 차이가 0 이하이고, RRF의 차이가 CC보다 작다 | 한국어 질문의 BM25 목록은 대부분 잡음이다. RRF는 잡음 목록의 1위도 dense 1위와 같은 무게로 섞고, CC는 잡음 목록의 점수가 낮으면 그만큼 덜 반영한다 |

## 조건

| 조건 | 검색 | 설정 |
|---|---|---|
| Dense(기준선) | dense 상위 k | 기존 실행 `baseline-4e6abaee3113`를 다시 쓴다 |
| BM25 단독 | BM25 상위 k | 토크나이저 `word`(Ingest와 같음), 질의 단어마다 1 |
| Hybrid-RRF | 같은 후보 묶음에 `score = Σ 1/(60 + rank)` | k = 60 |
| Hybrid-CC | 같은 후보 묶음에 `score = α·minmax(dense) + (1−α)·minmax(BM25)` | α = 0.5 |

- 두 Hybrid는 같은 후보를 쓴다. dense 상위 40개와 BM25 상위 40개를 한 번 가져와 코드에서 융합한다. 두 조건의 차이는 융합식뿐이다. Qdrant 서버의 RRF는 k를 정할 수 없고 후보 처리가 달라 쓰지 않는다.
- RRF의 k와 CC의 α는 둘 다 조정하지 않은 기본값이다. 한쪽만 조정하면 비교가 불공정하다. RRF의 k = 60은 RRF 원 논문(Cormack 외, 2009)의 값이다. CC의 α = 0.5는 두 점수를 같은 무게로 섞는 값이다.
- CC에서 한쪽 목록에만 있는 후보는 다른 쪽 정규화 점수를 0으로 둔다. 목록 안 점수가 모두 같으면 정규화 점수는 모두 1이다.
- 점수가 같으면 `chunk_id` 순으로 정해 같은 입력이면 같은 순위가 나온다.
- 후보 묶음 크기 40은 평가 깊이(Recall@10, nDCG@10)의 4배다. 서버 RRF 구현(`search_hybrid`)의 prefetch 비율과 같다.

## 판정 규칙

비교는 네 쌍이다. BM25 대 Dense, RRF 대 Dense, CC 대 Dense, CC 대 RRF. 문항별로 짝지은 차이(앞 조건 − 뒤 조건)의 bootstrap 구간을 Bonferroni로 보정해 **98.75% 구간**으로 본다.

| 판정 | 조건 |
|---|---|
| 지지 | 구간 하한 > 0 |
| 기각 | 구간 상한 < 0 |
| 판정 불가 | 구간이 0을 포함 |

- H0, H1, H2는 주 지표(Recall@5, 영어와 한국어를 합친 답 있는 문항 64개)로 판정한다. H0의 언어별, 유형별 부분은 아래 H3와 같은 방식(방향)으로 읽는다.
- 2차 지표(정확성)는 같은 규칙으로 판정한다. 두 조건에서 모두 답한 문항끼리 짝짓는다. 답한 문항이 60개 안팎이라 판정 불가가 나올 수 있고, 그대로 기록한다.
- H3는 언어별 문항이 32개이고 유형별로는 4~10개라 구간 판정을 하지 않는다. 한국어 Recall@5 차이(Hybrid − Dense)가 0 이하이고 RRF의 차이가 CC의 차이보다 작으면 예측대로라고 쓴다.
- 채택 규칙: 주 지표에서 Dense 대비 "지지"인 Hybrid만 채택 후보다. 둘 다 지지면 CC 대 RRF 판정을 따르고, 그것도 판정 불가면 정규화가 필요 없는 RRF를 고른다. 둘 다 지지가 아니면 Dense를 유지한다. BM25 단독은 해석용 조건이라 채택 후보가 아니다.
- 확인 조건: 네 조건의 검색 단계 거절 문항이 같아야 한다. 다르면 거절 판정이 검색 방식에 따라 바뀐 것이라, 원인을 찾기 전에는 결과를 해석하지 않는다.

## 분석 계획

- 검색 지표가 올랐는데 정확성이 그대로면 문항 단위로 나눈다. 근거가 상위 5개에 들어왔는데 틀린 답(생성 문제), 잘린 답(알려진 결함), 근거를 여전히 못 찾은 문항으로 센다.
- 조건마다 Dense 대비 새로 찾은 근거와 밀려난 근거를 문항별로 세어 순효과를 나눈다.
- 실패 사례 2~3건을 질문, 조건별 근거 순위와 함께 인용한다.

## 결정

사전 채택 규칙과 다르게, 질의 언어에 따라 검색 방식을 고르는 구성(routed: 한글이 있으면 Dense, 없으면 CC)을 서비스 기본값으로 채택했다. 결과를 본 뒤의 결정이라 근거를 순서대로 남긴다.

1. **판정 단위를 잘못 잡았다.** 서비스 범위는 영어 문서에 영어 질의가 기본이고, 한국어 질의는 추가 확인용이다. 사전 규칙은 이를 확인하지 않고 두 언어를 합친 64쌍을 판정 단위로 잡았다. 결과를 본 뒤 범위를 확인한 것이라 이 사실을 그대로 기록한다.
2. **영어만 같은 보정 수준(98.75%)으로 보면** CC − Dense는 nDCG@10 +0.079 [0.013, 0.157]로 지지, Recall@5 +0.122 [−0.013, 0.278]로 하한이 0에 근소하게 못 미쳐 판정 불가, 정확성 +0.097 [−0.065, 0.258] 판정 불가, 오거절률 −0.031이다. 나빠진 지표가 없고 검색 지연도 늘지 않았다.
3. **한국어는 Dense가 가장 낫다.** Recall@5와 오거절률 모두 Dense가 가장 좋고, 손해의 메커니즘(영어 문서와 한글 토큰의 불일치)은 실험 전에 H3로 예측했다.
4. **확인 실험(dev set, 검색 지표만, 95% 구간).** 언어별 선택은 test set 결과를 보고 정했으므로 같은 test set으로 좋다고 판정하면 점수가 부풀려진다. 이 결정에 쓰지 않은 dev set(답 있는 문항 영어 30, 한국어 30)으로 검색만 다시 쟀다. 원 자료: `research/artifacts/hybrid_fusion/dev_check.json`.

## 해석

- **합계가 판정 불가인 주된 이유는 언어별로 효과가 반대라서다.** 영어에서는 BM25를 섞은 세 조건 모두 Recall@5가 오르고(+0.09~+0.12), 한국어에서는 모두 내려간다(−0.02~−0.25). 영어와 한국어를 합친 64쌍에서 두 방향이 상쇄되고, 4쌍 보정(98.75%)으로 구간도 넓다.
- **영어 이득은 정확한 문자열에서 나온다.** trap 4문항은 BM25를 섞은 세 조건 모두 1.000이다. 예를 들어 "`[tool.uv] dev-dependencies` 아래 테스트 도구가 있는데 `uv add --dev`를 하면"이라는 문항은 Dense가 근거를 상위 5개에 넣지 못했고(Recall@5 0), 세 조건은 모두 찾았다(1.0). 10단계에서 근거가 8위라 거절됐던 사전 릴리스 Python 문항(`test-factual-01`)도 영어에서는 세 조건 모두 근거를 찾아 답했다(한국어는 네 조건 모두 찾지 못했다). multi_doc도 CC에서 0.675에서 0.825로 올라, 두 주제를 BM25가 각각 맞춘다는 가설의 방향과 맞는다.
- **한국어 손해는 BM25 목록이 잡음이라서다.** Corpus는 영어이고 `word` 토큰화는 한글 단어를 그대로 두므로, 한국어 질문의 한글 토큰은 문서와 거의 맞지 않는다(5단계 관찰과 같다). 한국어 질문의 BM25 최고 점수는 0.2 안팎으로, 영어(13~38)보다 두 자릿수 낮다. BM25 단독은 한국어 Recall@5가 0.443이고, 엉뚱한 근거를 받은 LLM이 근거 부족으로 거절해 생성 단계 거절이 8건에서 18건으로 늘었다(오거절률 0.097에서 0.406). 반대로 백틱 안의 영문 식별자가 남은 한국어 trap 문항은 올랐다(0.500에서 0.750).
- **RRF가 CC보다 한국어에서 더 나빴다(H3 예측대로). 다만 예측의 이유는 맞지 않았다.** 설계 때는 "CC는 잡음 목록의 낮은 점수를 덜 반영한다"고 적었지만, min-max 정규화는 목록마다 0~1로 다시 펴서 잡음 목록의 1위도 1.0이 된다. 실제 차이는 dense 쪽에서 난 것으로 본다(추정). dense는 정답 청크가 2위와 점수 차이를 크게 벌리는 경우가 있는데(예: 0.833 대 0.656), CC는 이 차이를 유지하고 RRF는 1/61과 1/62의 차이로 지운다. 한국어 summary 문항 "uv는 개발 의존성 그룹을 어떻게 처리하나요?"에서 Dense 1.0이 RRF 0.2, CC 0.6으로 떨어진 것이 이 경우다. 순위 지표(nDCG, MRR)에서 CC가 RRF보다 지지된 것도 같은 설명과 맞는다.
- **정확성은 어느 비교에서도 판정 불가다.** 답한 문항이 50~59개라 구간이 넓다. 방향은 CC가 가장 좋다(+0.089). 출력 상한에 닿은 답이 조건마다 7~11개라, 정확성 차이 일부는 검색이 아니라 잘림 여부에서 나올 수 있다.

## 한계

- RRF의 k와 CC의 α는 기본값 하나씩만 봤다. 다른 값에서는 결론이 달라질 수 있다.
- 조건마다 생성을 한 번만 돌렸다. 게이트웨이가 seed를 받지 않아 같은 조건을 다시 돌려도 답이 일부 달라질 수 있다.
- 유형별 문항은 4~12개라 방향만 읽는다. 언어별 분석은 사후 탐색이고 다중 비교를 보정하지 않았다.
- RRF 조건은 파일럿(Judge 2건)을 먼저 돌린 뒤 같은 커밋과 설정으로 나머지를 채웠다. 파일럿 판정도 같은 run에 저장돼 결과에 포함된다.

## 계획과 달라진 점

- 언어별 짝지은 비교를 결과를 본 뒤 추가했다(사후 탐색). 사전 판정에는 쓰지 않았다.
- 채택 결정을 사전 규칙(합계 Recall@5 지지)과 다르게 정했다. 서비스 범위가 영어 질의 기본임을 결과를 본 뒤 확인했고, dev set 확인 실험과 test set 실측을 더해 언어별 선택을 채택했다("결정" 절).
- 다섯 번째 구성(routed)을 결과를 본 뒤 추가했다. 사전 비교 쌍과 보정 수준에는 넣지 않고 확인 실험으로만 다뤘다.
- H3의 이유로 적은 "CC는 잡음 목록의 낮은 점수를 덜 반영한다"는 min-max 정규화와 맞지 않았다. 예측한 방향은 맞았고, 해석 절에 다른 설명을 추정으로 적었다.
