# 3. 벡터 데이터베이스 선정

**결론: Qdrant (`qdrant/qdrant:v1.20.0`, gRPC 연결)**

## 질문

이 서비스의 기능 요구를 만족하면서 운영과 구현이 가장 단순한 벡터 DB는 무엇인가.

## 후보

Qdrant, PostgreSQL + pgvector, Chroma. 모두 Docker Compose 내부 네트워크에서 버전을 고정해 띄웠다.

## 고정한 변인

- 청크: 고정 길이 1,000자, 587개
- 벡터: 임시 임베딩 bge-small-en(384차원). 1024, 1536차원은 같은 벡터를 무작위 투영해 만들었다
- 질의: dev set 38문항, top-10

임시 임베딩을 쓴 이유: 이 실험은 검색 품질이 아니라 기능, 지연, 자원, 근사 검색 오차를 본다. 이 값들은 벡터의 의미보다 개수와 차원에 좌우된다.

## 결과: 기능 검사(실제 호출로 판정)

| 기능 | 왜 필요한가 | Qdrant | pgvector | Chroma |
|---|---|---|---|---|
| 자연 키 upsert | Ingest를 다시 돌려도 같은 상태 | 통과 | 통과 | 통과 |
| 컬렉션 메타데이터 | 인덱스 계약(임베딩 모델, 토크나이저) 대조 | 통과 | 통과(별도 테이블) | 통과 |
| 메타데이터 필터 | 문서 단위 검색 | 통과 | 통과 | 통과 |
| sparse 벡터 | BM25 | 통과(IDF를 서버가 계산) | 통과(IDF는 직접 계산) | **실패** |
| dense + sparse 결합 검색 | Part C Hybrid 가설 | 통과(서버 내장 RRF) | 통과(RRF SQL 직접 작성) | **실패** |
| 정확 검색 모드 | 임베딩 비교에서 근사 오차 제거 | 통과 | 통과 | **실패** |

Chroma는 클라이언트에 sparse API가 있지만 오픈소스 로컬 서버가 sparse 인덱스 생성을 거부했다. 문서만 읽었다면 통과로 판정했을 항목이다.

## 결과: 성능

- 검색 지연 p95는 세 후보 모두 5ms 이하, 적재는 1초 남짓이다. LLM 생성(초 단위)에 비하면 결정 요인이 아니다.
- ANN 재현율@10은 Qdrant 1.0, pgvector 0.9974 이상이다. 이 규모(587개)에서는 Qdrant가 HNSW를 만들지 않고 전수 비교해 사실상 정확 검색이다.
- 메모리는 Qdrant가 가장 크다(적재 후 282~417MiB, pgvector 57~80MiB).

## 측정 중 발견한 문제: Qdrant REST 지연

처음 측정에서 Qdrant REST 연결의 지연이 차원과 상관없이 46ms로 일정했다. 차원이 4배가 돼도 그대로라 검색 연산이 아닌 통신 계층 문제로 보고 따로 진단했다. 같은 코드에서 REST는 45.35ms, gRPC는 0.42ms였다. 이후 측정과 구현은 gRPC로 한다.

교훈: 수치가 변인에 반응하지 않으면 측정 대상이 아니라 측정 경로를 의심한다.

## 결정과 이유

미리 정한 순서(기능 통과, ANN 재현율 0.99 이상, 운영 단순성, 지연)를 따랐다.

1. Chroma는 기능 검사에서 탈락했다.
2. Qdrant와 pgvector는 재현율을 모두 통과했다.
3. 운영 단순성에서 갈렸다. Qdrant는 BM25의 IDF와 RRF 결합 검색을 서버가 제공한다. pgvector로 같은 기능을 만들려면 문서 빈도 통계를 직접 관리하고 RRF를 SQL로 써야 한다.

감수한 점: 메모리 사용량이 가장 크고, gRPC 연결을 강제해야 한다.
